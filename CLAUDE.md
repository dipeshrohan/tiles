# CLAUDE.md

Guidance for Claude Code working in this repository.

## What this is
Tiles is a browser app for industrial R&D and shopfloor teams: a factory ontology with Git-style change history, physics-based virtual sensors, a correlation finder, a design studio and a copilot. It is currently front-end only, with seeded synthetic data. The roadmap (docs/ROADMAP.md) adds a Python backend and real plant data.

## Commands
- `npm run build`: Vite build of `js/app.ts` into `js/tiles.bundle.js` (one classic script, so `index.html` works from `file://`). **Required after editing anything in `js/`**; `npm test` fails if the bundle is stale. `npm run dev` rebuilds on save.
- `npm run lint`: ESLint and Prettier check. `npm run format` fixes formatting and rebuilds.
- `npm run typecheck`: strict TypeScript (`tsc`, includes `noUncheckedIndexedAccess`).
- `npm test`: Vitest unit tests, including the bundle freshness check.
- `npm run test:e2e`: Playwright smoke tests. In Claude Code cloud sessions Chromium is preinstalled; do not run `playwright install` there.
- `npm start`: serve on http://localhost:5173.
- `docker compose up --build --wait`: full stack (TimescaleDB, Redis, API on 8000, web on 5173); `docker compose down -v` resets it. In cloud sessions Docker Hub may rate-limit and the TLS proxy breaks in-container `pip`; see CONTRIBUTING for the workaround.
- Backend (`api/`, Python 3.12+, managed with `uv`): `uv sync`, then `uv run tiles-api` (port 8000), `uv run pytest -W error`, `uv run mypy` (strict), `uv run ruff check .` and `uv run ruff format .`. Run them from `api/`. Database tests need `TILES_TEST_DATABASE_URL` (they are skipped locally without it and fail in CI). Schema changes go in a new migration: `uv run tiles-migrate revision "…"`.
- Edge agent (`edge/`, Python 3.12+, `uv`): `uv sync --all-extras`, then the same `uv run pytest -W error`, `uv run mypy`, `uv run ruff check .` and `uv run ruff format .`, run from `edge/`. The SQL connector tests start PostgreSQL and SQL Server in Docker (`tests/sql_servers.py`); without Docker they are skipped, except with `TILES_EDGE_TEST_DOCKER=1` (set in CI), where they must run. The SQL Server driver needs `libltdl7 libkrb5-3 libgssapi-krb5-2`.

## Layout
- `js/lib/*.ts`: pure logic in strict TypeScript (ontology, physics, analysis, design models, copilot routing, stats, charts). Shared types in `js/lib/types.ts`. Import with the `.ts` extension. Unit-tested in `test/`.
- `js/lib/canvas.ts`: the ontology canvas at scale (T2.14): folding by hierarchy (`contains`, `controlledBy`, `emits`), the column layout that wraps tall columns, search, and the view box for zoom and pan; the Ontology page draws it and handles the wheel, drag and double-click. `test/fixtures/large-plant.js` is a 2,069-node plant for tests.
- `js/lib/csv.ts` and `js/lib/importer.ts`: the CSV parser and the bulk-import logic (column mapping, time formats and zones via `Intl`, readings in batches) behind the Import data page (`js/views/imports.ts`), which reads the file in the browser and sends it to the API. The Signals page (`js/views/signals.ts`) is the catalogue's browser side; the Data explorer (`js/views/explorer.ts`) plots signals with `timeChart` from `js/lib/svg.ts`, from `api_series.py` (T2.10: raw readings, or `time_bucket` averages with min and max). The Warnings page (`js/views/warnings.ts`, logic in `js/lib/warnings.ts`) is the warnings inbox (T3.08): filters, the signal around a warning (`timeChart` with threshold and baseline `levels` and the warning as a shaded `span`), its payload and activity, and the workflow steps. The Shopfloor page (`js/views/shopfloor.ts`, logic in `js/lib/shopfloor.ts`, T5.16) is the same warnings for a tablet on the line: placed on their machines through the ontology (Signal ← emits PLC ← controlledBy Machine), worst first, with 64 px buttons, a machine board, a 30 s refresh and a full view (`body.floor-full`). The Plant page (`js/views/plant.ts`, logic in `js/lib/plant.ts`, T5.17) is the site → workcenter → line → machine navigator over the same hierarchy (`#/plant/<node id>`), with warnings rolled up and a sheet per machine. Both share the open warnings and the catalogue's linked signals through `js/views/floor-data.ts`, and the cached edge index in `js/lib/graph-index.ts`.
- `js/views/*.ts`: one module per page; each default-exports a `View` (`{ id, title, icon, render(ctx), bind(root, ctx) }`, see `js/views/types.ts`). Per-page UI state goes through a typed `uiState(ctx)` helper with defaults.
- `js/app.ts`: state, router, persistence (localStorage via `js/lib/store.ts`).
- `js/lib/api.ts`: typed client for the Tiles API (`createApiClient`, `ApiError`) and the data-source flag (`local` or `api`, set in Settings or with `?api=<url>`). Views reach it as `ctx.api`, which is null in local mode; failed calls already show a toast.
- `js/lib/ontology-store.ts`: the ontology page changes `state.repo` only through `ctx.ontology.act(store => …)`, where the store is local (this browser) or remote (the API, reloaded after each change). Browser tests use the in-memory fake API in `e2e/fake-api.js` (which can also play the sign-in provider).
- `js/lib/oidc.ts`: browser sign-in (Authorization Code + PKCE, tokens in sessionStorage, refreshed before expiry); `ctx.auth` exposes it.
- `vite.config.js`: builds the IIFE bundle and configures Vitest. `scripts/check-bundle.js` compares a fresh build with the committed bundle.
- DOM helpers in `js/lib/dom.ts`: `need()` (querySelector that throws if missing), `field()` (form values), `onAll()` and `onSubmit()` (typed event wiring). Prefer them over raw querySelector in views.
- `server.js`: static server; exports `createTilesServer({ apiUrl })` for tests. With `TILES_API_URL` it writes the API into index.html's `tiles-api` meta tag, which the app opens by default (`resolveDataSource`).
- `Dockerfile` (root) is the web image: only index.html, css, the bundle and server.js. `deploy/helm/tiles/` is the Helm chart (T5.09): the API (each pod runs `tiles-migrate upgrade` as it starts; migrations, and the `tiles_grant_app()` after them, hold an advisory lock, `db.MIGRATION_LOCK`, in `migrations/env.py`), the jobs as CronJobs, the web app, and a bundled TimescaleDB and Redis for evaluation; secrets reach the API as files (`TILES_SECRETS_DIR`), and a generated Secret (kept across upgrades with `lookup`) holds the bundled database's password and a data key. Templates aren't checked by Prettier; CI's Helm job lints, validates with kubeconform and installs on kind. `.github/workflows/images.yml` publishes the images to GHCR.
- `api/src/tiles_api/`: FastAPI service. `main.py` has `create_app(settings)` and the request-ID/JSON-logging middleware; `settings.py` reads `TILES_*` env vars; `logging.py` is the JSON formatter; `auth.py` checks OIDC bearer tokens (dev identity outside production) and `identity.py` turns them into users and site roles; `api_sites.py` creates sites (T6.06: `OrgAdmin`, an organisation admin or a `tiles-admin` sign-in, the one write dependency that isn't a site's; audited in the new site) and works out a site's onboarding progress (`GET /sites/{id}/onboarding`), which the browser's wizard (`js/views/onboarding.ts`, logic in `js/lib/onboarding.ts`) follows; write endpoints take `Editor` (engineer or above) or `Admin` instead of `Ctx`, so a new write endpoint must use one of them and record itself with `ctx.audit(...)` (`audit.py`); the one exception is a user's own data that changes nothing on the site (copilot conversations: `Ctx`, still audited), and creating a site, which has none yet (`OrgAdmin` in `api_sites.py`, audited with `audit.record` in the new site); `db.py` runs the Alembic migrations in `migrations/versions/` (plain SQL, no ORM); `ontology.py` ports `js/lib/ontology.ts`, `ontology_store.py` persists it and `api_ontology.py` serves it; `api_reviews.py` is the change-approval workflow (T2.12): staged ops become a numbered change request (migration 0008) that another engineer approves (committing it, with the reviewer on the commit) or rejects, and a site can require it for every change (the browser side is `js/views/reviews.ts`, with the diff text from `js/lib/review.ts`). `ontology_io.py` is bulk import and export (T2.13): the committed graph as JSON or CSV, and a file planned into ops (merge or replace) that are staged, served by `api_ontology_io.py`. Both ontology implementations must pass `test/fixtures/ontology-parity.json`; change them together. Tests in `api/tests/` use `TestClient(create_app(settings))`.
- `edge/src/tiles_edge/`: the on-site edge agent (ADR 003). Standard library only, so it also ships as one zipapp file; it only connects out. `config.py` reads the TOML config, `client.py` posts to Tiles (TLS verified; https except to localhost), `agent.py` runs the heartbeat loop with backoff and starts the connectors, `cli.py` has `run`, `check` and `opcua cert|server-cert|browse`. Connectors that need a protocol library are extras, imported only when configured (`connectors.py`): `opcua.py` (asyncua; the server certificate is always pinned), `mqtt.py` (paho-mqtt over TLS; `value`, `json` and Sparkplug B payloads, decoded by the stdlib `sparkplug.py`) and `sql.py` (polls `[[sql.queries]]` from a saved watermark; sqlite from the standard library, psycopg for PostgreSQL, Microsoft's mssql-python for SQL Server; read-only, every poll rolled back) feed `samples.py`'s buffer; `run` puts their samples in `buffer.py` (SQLite on disk, bounded, survives restarts; it also keeps the SQL watermarks, saved with their samples) and `forwarder.py` sends the oldest in batches to `POST /agent/samples`, deleting them only once accepted. The API side is `api_agents.py`: admins register agents (the token is shown once; only its hash is stored) and agents call `POST /agent/heartbeat` with their own token, reporting their connectors and buffer. `api_samples.py` serves `POST /agent/samples`: a batch of readings goes into the `samples` hypertable (migration 0004: compression after 7 days, retention 5 years) in one statement, skipping ones already stored, and new tags are added to `signals`. `api_imports.py` serves file imports (T2.07): an engineer starts an import, sends its readings in batches through the same storing step, and finishes it; the `imports` table (migration 0005) keeps who imported what and the counts. `api_signals.py` is the signal catalogue (T2.08): search a site's signals with their latest reading, and (engineers) set a signal's unit, sample rate, description and link to a committed Signal node (one tag per node, migration 0006), audited. `quality.py` is the data-quality check (T2.09): gaps, stuck values, out-of-range values, source-flagged readings, unit mismatches and silent edge tags over a window ending at each signal's latest reading, computed in one SQL statement per signal; the latest report per signal is kept in `signal_quality` (migration 0007, which also adds the expected range and stuck limit to `signals`). It runs from `POST /sites/{id}/signals/quality`, after a signal edit that affects it, and from the `tiles-check-quality` command. `suggest.py` is agentic ingestion v1 (T2.11): for each unmapped tag, a link to a free Signal node or a new one under the PLC of sibling tags or of the machine the tag names; deterministic, explained, scored against `api/tests/fixtures/suggestions.json`, served by `api_suggest.py`.
- `api/src/tiles_api/models/`: the model registry (T3.01): `registry.py` (specs with inputs, outputs per sample or per window, bounded parameters; `evaluate` checks them), `store.py` (an organisation's `models` row for a version, written on first use and never rewritten), `published.json` (each published version's spec fingerprint: a unit test fails if one changes or a new version isn't pinned), and the models themselves, registered with `@register` on import (`design.py`, T4.10: the Design Studio's `cell-swelling` and `joint-actuator` versions as `design` models, matched to `js/lib/design.ts` by `test/fixtures/design-models.json`, made by `test/design-parity.test.js`; `plunger.py`, T3.02, matched to `js/lib/physics.ts` by `test/fixtures/plunger-shots.json`, made by `test/plunger-parity.test.js`). Served by `api_models.py`. `api_runs.py` is design runs (T4.11, migration 0020): a design model version run on parameters, its output computed by the API, numbered per site with its parent, the run it restored, note and author, never changed; restore runs an earlier run again after the model's latest, compare gives the changes and output differences (`ctx.api.runs` in the browser). Runs belong to a site's shared design project (T4.14, migration 0022, `/design-projects`); with the API the Design Studio (`js/views/design.ts`, mapping in `js/lib/design-runs.ts`) saves and lists runs per project, otherwise in the browser. The audit export (T4.13) is `GET …/runs/{n}/audit` (the lineage and the runs it restored, model specs, a SHA-256 digest of the runs) and `…/audit.pdf`, written by `pdf.py` (standard library only). `sweeps.py` is sweeps as background jobs (T4.12, migration 0023): a grid of one or two parameters run in chunks with progress, cancel and a heartbeat, the result kept and given again for an identical sweep; `api_sweeps.py` starts them in the background, and `tiles-run-sweeps` picks up any left behind. `runner.py` is the model runner (T3.03): `model_bindings` (migration 0009) feed a model version's inputs from signals (or `@time`), readings are joined on time and cut into gap or fixed windows, complete windows run, and outputs go to derived signals `<binding>.<output>` from `done_until` on; `tiles-run-models` runs every enabled binding (from cron), `api_model_bindings.py` binds, runs and stops them.
- `api/src/tiles_api/detection.py`: streaming detection (T3.04), pure: rolling robust baseline (median, MAD; `flat_spread` when it is 0), `k`, `persist`, `direction`, `cooldown`, with its state saved between runs; matched to the browser's `detectFrictionAlerts` by `test/fixtures/friction-detection.json` (`test/detection-parity.test.js`). `detector_job.py` feeds detectors (migration 0010: `detectors`, `warnings`) new readings and records warnings (`tiles-detect`); `api_detectors.py` serves detectors. `api_warnings.py` serves warnings and their workflow (T3.07, migration 0011): raised, acknowledged, assigned, resolved with an outcome (true alarm, false alarm, unknown) and reopened, each step and comment kept in `warning_activity` and audited; this status is separate from whether the signal is still out (`ended_at`), which only the detector job sets. `notify.py` is notifications (T3.09): messages about a warning raised (recent ones only) or assigned are queued in the `notifications` outbox (migration 0012) in the same transaction, and `tiles-notify` sends them by SMTP or to the site's Teams webhook (only Microsoft's webhook hosts), retrying, then giving up; `api_notifications.py` serves the preferences, the Teams channel (whose URL is never shown again) and the outbox. The Settings page has the browser side. `performance.py` is warning performance (T3.10, migration 0013): events are readings on signals with an `event_kind` (downtime, scrap, other; the value is the code), matched by `asset` (set on signals and detectors) to detectors' warnings and scored with `backtest.score`, with what people resolved them as; `api_performance.py` serves `GET /sites/{id}/performance`, and the Warning performance page (`js/views/performance.ts`, logic in `js/lib/performance.ts`) shows it. `correlate.py` is the correlation finder (T3.11), pure: Cohen's d with its 95% interval and the point-biserial r, per variable and segment, matched to the browser's `correlationFinder` by `test/fixtures/correlation.json` (`test/correlation-parity.test.js`); `api_datasets.py` serves batch tables (`datasets`, `dataset_rows`, migration 0014) and runs it; the Correlation finder page (`js/views/correlate.ts`, logic in `js/lib/datasets.ts`) uploads a CSV and shows the effects as a forest plot. `api_insights.py` is saved insights (T3.12, migration 0015): a finding saved with its query (a correlation or signals over a range), the evidence the API computes from it (kept as it was) and proposed actions, numbered per site and accepted or rejected by another engineer; the Insights page (`js/views/insights.ts`, logic in `js/lib/insights.ts`, linked as `#/insights/<number>`) shows them, and the correlation finder and Data explorer save them. `wear.py` is the wear check (T3.13), pure: bucket medians, the baseline against the recent level (the browser's `wearCheck` on hourly buckets, matched by `test/fixtures/wear-check.json`, made by `test/wear-parity.test.js`), the Theil–Sen slope and the time to a limit; `api_wear.py` serves `POST /sites/{id}/signals/{signal}/wear-check`, and the Data explorer runs it on each chart (`js/lib/wear.ts`). `assistant.py` is the copilot's conversation loop (T4.01): Claude with tool use behind a `Model` protocol (`AnthropicModel` wraps the official SDK's streaming; tests script a stand-in), tool rounds until an answer; `copilot_tools.py` has the tools (T4.02: site overview, signal search, ontology graph query and health check, time series, wear check, virtual sensors, warnings and events, correlation; read-only, one short transaction per call, as the user who asked; a tool that can't answer raises `ToolError` with words the model can act on; for engineers and admins also `propose_ontology_change`, T4.09, the one that writes: it opens a change request through `api_reviews.open_request` with `source` "copilot" (migration 0021), which the person who asked can't approve, so it is never committed without another engineer); `grounding.py` is the grounding check (T4.03), pure: tool results are labelled `[n]` and cited by the answer, and every number and `code` name in it must be in a cited result or the question, or it is withdrawn and asked again once (`respond`), then kept with its report (migration 0017, `meta`); `api_copilot.py` serves each user's conversations (migration 0016) and streams answers as server-sent events, storing every message; the copilot is off until `TILES_ANTHROPIC_API_KEY` and `TILES_COPILOT_MODEL` are set. `copilot_usage.py` is cost and latency (T4.07): `AnthropicModel` caches the prompt (`assistant.cached`), a question stops at its token budget or when its organisation's daily budget runs out (`respond(budget=, stop=)`, in `assistant.billed` tokens, weighted by price), and every question is a `copilot_usage` row (migration 0019) that per-organisation and per-user rate limits and the organisation's daily token budget count (429 with Retry-After); admins read it at `GET …/copilot/usage`, shown on the Settings page (`js/lib/copilot-usage.ts`). Users rate answers (`copilot_feedback`, migration 0018; admins list them). The Copilot page (`js/views/chat.ts`, logic in `js/lib/copilot-chat.ts`, events read by `js/lib/sse.ts`) streams answers with their tool traces, citations linked to them, evidence links, withdrawn drafts and grounding warnings, and falls back to the built-in skills (`js/lib/copilot.ts`) without the API or its copilot. `jobs.py` runs a scheduled job over many items (bindings, detectors), one transaction each. `backtest.py` is the backtest (T3.05): it replays history with each combination of settings (baselines computed once per window, from a sorted window, exactly as the detector's; then `detection.judge`) and scores the warnings against events (recall, precision, false per day, warning time, the same matching as the browser's `scoreAlerts`), with a Markdown report; `api_backtest.py` serves it (`POST /sites/{id}/backtest`) and has `tiles-backtest`.
- `api/src/tiles_api/loadtest.py`: the load test (T5.15), `tiles-loadtest prepare` (registers `load-N` agents) and `run` (agents at N signals × rate, users browsing; Markdown report, exit 1 on a missed target); results and sizing in `docs/load-test.md`. It found that sync handlers could stall when requests outnumbered connections: `store.db_slot` (an async dependency of `get_conn`) now queues them for a connection without holding a worker thread, then 503 after `TILES_DB_WAIT_SECONDS`; work outside a request (copilot streams, sweeps) uses `store.side_pool`, never the requests' pool. `TILES_WORKERS` runs several API processes (Helm `api.workers`).
- `docs/install.md` (T5.12) is the customer-hosted install guide; CI's "Install dry run" job follows it on a new kind cluster (the customer-hosted Terraform: apply, checks, an unchanged second plan, a secret change restarting the API, destroy refused while Terraform holds the data key), so change them together.
- `deploy/terraform/` (T5.10): `modules/tiles` (the chart and its settings Secret on any cluster; a generated data key in state unless `existing_secret`), `modules/azure` (AKS, logs, backup storage; TimescaleDB stays in the cluster, as Azure's managed PostgreSQL lacks its columnstore), `environments/managed-azure/{cluster,tiles}` (two stages: providers are never configured from a cluster made in the same run) and `customer-hosted`. The generated data key has `prevent_destroy`, so `terraform test` runs that make one only plan (`override_resource` during plan). `terraform test` with mock providers in each module's `tests/`; CI's Terraform job runs fmt, validate, test and `trivy config`. Locally the registry is blocked: use a filesystem mirror from releases.hashicorp.com.
- `deploy/backup/pitr-drill.sh`: the restore drill (T5.14), run by CI's Restore drill job: on Docker, a TimescaleDB server archiving its WAL gets the schema and readings, a base backup, more readings, then a mistake; a new server replays the archive to just before it and the drill checks every reading is back. `docs/runbooks/backups.md` is the backup policy (pgBackRest or a managed service, 35 days of point-in-time recovery) and the restore procedure.
- Releases (T6.04, `docs/releasing.md`): one version everywhere, kept by `scripts/version.js` (`npm run version:check` in CI; `set X.Y.Z` writes it); `CHANGELOG.md` (add user-visible changes to the top section, the next version marked Unreleased; a release dates it); `scripts/upgrade-test.sh <ref> <db url>` migrates an older version's database and data (`scripts/upgrade_check.py`) to head and back, run from main in CI's API job; `.github/workflows/release.yml` publishes a tag's release.
- Monitoring (T5.13): `telemetry.py` sets up OpenTelemetry when `OTEL_EXPORTER_OTLP_ENDPOINT` is set (spans for requests, tagged `tiles.request_id`, and statements; metrics: ingest readings and delay, agents' buffer gauges from their heartbeats, the jobs' last runs from `job_runs` (migration 0026, written by `@telemetry.job_main`) and the notification outbox, read from the database by the API). The alert rules and dashboard are in `deploy/helm/tiles/files/` (the chart installs them; `deploy/monitoring/alerts.test.yaml` is their promtool test, run in CI); `deploy/monitoring/` has the collector configuration. New metric or rule: update `deploy/monitoring/README.md`.
- `docs/guides/` (T6.05): user, admin and model-author guides, and `api.md`/`openapi.json` generated by `tiles-apidoc` (`apidoc.py`; `tests/test_apidoc.py` fails when they are stale or an endpoint has no docstring, so run `uv run tiles-apidoc` after changing endpoints).
- `docs/`: roadmap, task list, ADRs, and `data-model.md` (node types and relationships, mapped to ISA-95). Adding a node type means changing `NODE_TYPES` in both `js/lib/ontology.ts` and `api/src/tiles_api/ontology.py` plus a migration for the database check.

## Rules
- Add or update tests with every behaviour change; never skip or disable a test.
- A site's data is under row security (T5.04, migration 0024), closed when no site is named: a new table with a `site_id` needs a forced `site_rows` policy in its migration, and a table that belongs to a site through a parent needs one through the parent (`tests/test_row_security.py` fails otherwise). Requests are scoped by `SiteContext`; a pooled connection used outside one must scope itself (`store.scope_to_site`); jobs connect with `options=store.UNSCOPED`; widen with `store.all_sites` only for what spans sites. The API reads readings from the `site_samples` view and stores them with `tiles_store_samples`, never the `samples` table.
- Credentials stored in the database are sealed with a data key (`sealed.py`, T5.06; `sealed.seal`/`unseal` with a context naming the row) and never shown again; settings that hold secrets are `SecretStr`. See `docs/runbooks/secrets-and-encryption.md`.
- Keep the browser app free of runtime dependencies.
- Escape any interpolated text with `esc()` when building HTML strings.
- Pages must pass `e2e/a11y.test.js` (axe, WCAG 2.1 AA, light and dark; T5.18): real buttons and links, labelled fields and table headers (`sr-only` for an action column), charts from `js/lib/svg.ts` (each gets a name and a summary of its numbers; pass a `title`), text colours that meet 4.5:1 (`--warn-ink` for text, `--warn` only for lines), underlined links in running text. See CONTRIBUTING.
- Task IDs (T1.01 …) map to GitHub issues; reference the issue in PRs.
